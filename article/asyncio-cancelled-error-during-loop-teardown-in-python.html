Asyncio CancelledError During Loop Teardown in Python

When an asynchronous task raises an unhandled cancellation error during event loop teardown in Python, the event loop's behavior depends on whether the loop is still actively running cancellation routines or if it has already been terminated. This article examines what occurs under the hood when a CancelledError goes unhandled during shutdown, detailing the transition between standard task cancellation, default exception handlers, garbage collection warnings, and potential resource leaks.

The Mechanics of Event Loop Teardown

During a standard shutdown—such as executing asyncio.run()—the runtime initiates teardown by retrieving all currently pending tasks, issuing a cancel() request to each, and running the loop until these tasks finalize. Under normal circumstances, a task receives the cancellation request, raises asyncio.CancelledError at its current await point, and unwinds its call stack cleanly.

The standard teardown routine gathers these tasks using asyncio.gather(*tasks, return_exceptions=True). In this managed phase, asyncio.CancelledError is explicitly caught and suppressed by the gathering process because cancellation is the expected path to completion during shutdown.

Unhandled Cancellation and Premature Closure

When an unhandled cancellation error occurs in an abnormal teardown scenario—such as manually stopping the loop via loop.stop() and loop.close() before awaiting remaining tasks—the cancellation cannot be resolved gracefully.

  1. Invocation of the Event Loop Exception Handler
    If a task is canceled but does not terminate prior to the loop closing, or if a custom runner fails to consume the resulting CancelledError, the task remains in an unresolved state. If the task raises an exception (or propagates a CancelledError outside an awaited context), the event loop calls loop.call_exception_handler(). The default handler logs an error containing the task object, the exception details, and the traceback via Python's standard logging module.

  2. The "Task was destroyed but it is pending!" Warning
    If the loop is closed while tasks are still awaiting cancellation completion, the tasks become orphaned. When Python's garbage collector later reclaims the memory of these abandoned task objects, it detects that the coroutines never ran to completion. The runtime emits a standard warning to stderr:
    Task was destroyed but it is pending!
    This warning indicates that an asynchronous routine was terminated abruptly without allowing its finally blocks or context managers to execute.

  3. RuntimeError: Event loop is closed
    If an asynchronous task catches asyncio.CancelledError to perform cleanup actions (such as closing database sessions or flushing network buffers), those cleanup routines often invoke loop methods (like await connection.close()). If the teardown logic has already closed the loop, the task's cleanup code fails immediately by raising RuntimeError: Event loop is closed. This secondary unhandled exception overrides the initial cancellation and propagates directly to the runtime.

  4. Resource and State Inconsistencies
    Because CancelledError inherits from BaseException rather than Exception (as of Python 3.8), it is designed to bypass general except Exception: catches. If teardown fails to let tasks process this exception to completion, any code located in deferred execution paths, asynchronous context managers (__aexit__), or standard finally clauses will not run. This leaves underlying OS handles, sockets, and subprocesses unclosed until the entire Python process terminates.

In summary, an unhandled cancellation error during loop teardown triggers logging warnings from the loop's exception handler, prevents clean execution of asynchronous cleanup blocks, risks generating RuntimeError: Event loop is closed during secondary operations, and results in garbage-collection warnings accompanied by resource leakage.
