How get_type_hints Works with Python Dataclasses

Python's typing.get_type_hints() function interacts with @dataclass classes by evaluating and resolving stringified annotations, inheritance chains, and forward references into actual runtime Python types. While the @dataclass decorator uses a class's __annotations__ attribute during class creation to determine which attributes become fields, inspecting those fields at runtime via raw annotations often produces incomplete or unresolved strings. get_type_hints() bridges this gap by traversing the class hierarchy, handling deferred type evaluation, and properly representing special annotations such as InitVar and ClassVar.

Resolution of Stringified Annotations and Forward References

When using from __future__ import annotations (PEP 563) or quoting type hints as strings, the class's __annotations__ dictionary stores the hints as plain strings rather than type objects.

When the @dataclass decorator processes the class definition, it reads these annotations to generate methods like __init__, __repr__, and __eq__. However, it does not resolve string references into runtime types; it merely stores the strings directly into each field's Field.type attribute.

Calling typing.get_type_hints(MyDataclass) dynamically evaluates these string expressions within the appropriate local and global namespaces, returning a dictionary mapping attribute names to real type objects (such as int, list[str], or custom class types).

from __future__ import annotations
from dataclasses import dataclass, fields
from typing import get_type_hints

@dataclass
class User:
    id: int
    profile: Profile  # Forward reference resolved at runtime

@dataclass
class Profile:
    bio: str

# __annotations__ contains raw strings: {'id': 'int', 'profile': 'Profile'}
# fields(User)[1].type is 'Profile' (str)

# get_type_hints resolves 'Profile' to the actual Profile class object:
hints = get_type_hints(User)
# Result: {'id': <class 'int'>, 'profile': <class '__main__.Profile'>}

Class Inheritance and the MRO

Dataclasses often inherit fields from parent dataclasses. Raw __annotations__ on a subclass only contains attributes defined explicitly on that subclass, omitting inherited fields.

typing.get_type_hints() follows the Method Resolution Order (MRO) in reverse order, collecting and resolving annotations from all base classes before applying the subclass annotations. Consequently, running get_type_hints() on a child dataclass produces a unified dictionary containing the resolved types of all inherited and local fields, mirroring how the dataclass constructor constructs its parameter list.

Behavior with ClassVar and InitVar

Dataclasses introduce specific wrappers that alter how attributes are handled during class construction:

  • ClassVar: Attributes wrapped in typing.ClassVar are ignored by @dataclass when generating instance fields. However, get_type_hints() still includes these attributes in its return value because they remain class-level annotations.
  • InitVar: Attributes wrapped in dataclasses.InitVar indicate initialization-only parameters passed to __init__ and __post_init__. get_type_hints() returns these entries wrapped in their InitVar type (e.g., dataclasses.InitVar[int]), allowing runtime inspection libraries to differentiate between regular instance attributes and init-only arguments.

Aligning get_type_hints() with dataclasses.fields()

Because dataclasses.fields(cls) preserves whatever was in __annotations__ at the time of decoration, relying on field.type for type-checking or serialization can cause errors when annotations are strings.

The standard approach for runtime inspection of dataclasses is to call get_type_hints(cls) first, and then map those resolved types back to the corresponding Field objects obtained from dataclasses.fields(cls). This ensures that field metadata (like default values, factories, and kw_only flags) is matched with fully resolved, executable Python types.
