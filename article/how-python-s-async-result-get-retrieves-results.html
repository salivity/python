How Python's AsyncResult.get() Retrieves Results

Python's multiprocessing.pool.AsyncResult.get() retrieves computation results from asynchronous worker processes by combining inter-process communication (IPC) pipelines, background management threads, and thread-level synchronization primitives. When a task is dispatched, the parent process tracks the pending job using an internal cache and a threading event. Calling .get() blocks the invoking thread until the pool's internal result handler reads the serialized payload from an IPC pipe, sets the stored value, and signals the event to unblock and return the result or re-raise any remote exceptions.

The Lifecycle of an Asynchronous Task

When a function is scheduled using asynchronous pool methods like apply_async(), the multiprocessing.Pool creates an AsyncResult instance. The pool assigns this instance a unique job identifier and registers it inside an internal dictionary called _cache. Simultaneously, the task and its arguments are serialized using pickle and placed onto the pool's incoming task queue for worker processes to consume.

The Background Result Handler Thread

Worker processes run in separate memory spaces. Once a worker finishes executing a task, it writes a tuple containing the job identifier, a success boolean flag, and the return value (or the captured exception) to an OS-level pipe.

The parent process runs a dedicated background thread known as the result_handler. This thread continuously monitors the pipe using system calls like select or poll. When data arrives from a worker:

  1. The result_handler deserializes the tuple.
  2. It looks up the corresponding AsyncResult instance in _cache using the job ID.
  3. It removes the job ID from _cache.
  4. It calls an internal callback method on the AsyncResult object, passing the computed payload and status flag.

Synchronization via threading.Event

Inside AsyncResult, synchronization is governed by an internal threading.Event object (often referenced as self._event). When the AsyncResult is initialized, this event is in an unset (cleared) state.

When you call AsyncResult.get(timeout=None):

  1. The method invokes self.wait(timeout).
  2. self.wait() delegates directly to self._event.wait(timeout), suspending the calling thread so it consumes no CPU cycles while waiting.
  3. If the timeout expires before the event is signaled, get() raises a multiprocessing.TimeoutError.
  4. When the result_handler receives the output from the worker pipe, it stores the payload in self._value, updates self._success, and calls self._event.set().
  5. Setting the event unblocks the calling thread waiting inside self._event.wait().

Error Propagation and Return

Once unblocked, AsyncResult.get() checks the boolean flag self._success. If the worker executed the task without error, self._success is True, and get() simply returns self._value.

If the worker encountered an unhandled exception during execution, the worker captures the exception and its traceback, sending it across the pipe instead of a standard return value. In this case, self._success is False. Upon waking, get() identifies the failure and immediately re-raises the stored exception in the calling process, allowing the parent application to handle worker-side errors using standard try...except blocks.
