Python ast.parse and compile Execution Behavior

This article explores the mechanics and runtime behavior of dynamically injected code using Python's ast.parse() and compile() functions. When dynamic code is introduced into an application via an Abstract Syntax Tree (AST) and subsequently compiled, it moves through distinct parsing, mutation, bytecode translation, and evaluation phases. Understanding this execution model is critical for developers implementing metaprogramming, domain-specific languages, plugin engines, or static analysis tools where code execution must remain deterministic, observable, and secure.

The Parsing and Compilation Lifecycle

The lifecycle of dynamic execution via the AST involves three primary stages: parsing source text into a tree, compiling that tree into a code object, and evaluating the code object within an interpreter frame.

  1. AST Generation (ast.parse): The ast.parse(source, filename='<unknown>', mode='exec') function converts raw string code into a tree of Python AST nodes without executing any instructions. It verifies grammatical syntax; if syntax errors exist, a SyntaxError is raised immediately.
  2. Compilation to Bytecode (compile): The standard built-in compile() function accepts an AST object (ast.AST) directly. It traverses the node hierarchy and generates a low-level Python code object (types.CodeType). During this step, Python performs symbol table analysis, assigns variable scopes (such as resolving local vs. global variables), and produces CPython bytecode instructions.
  3. Execution (exec or eval): The generated code object is fed into exec() or eval(). The Python Virtual Machine (PVM) creates an execution frame and processes the bytecode sequentially.

Scope Resolution and Namespace Binding

The execution behavior of a compiled AST is dictated heavily by the namespaces passed to exec() or eval().

  • Implicit Namespaces: If exec(code_object) is called without passing explicit globals and locals dictionaries, the dynamic code executes within the caller's current scope. It can read, create, or overwrite variables directly inside the caller’s local and global environments.
  • Explicit Namespaces: Passing separate dictionaries—exec(code_object, custom_globals, custom_locals)—isolates the dynamic code's runtime storage. Any dynamic variable assignments are stored inside the provided dictionaries rather than polluting the host frame.
  • Built-in Access: Even when empty dictionaries are passed for namespaces, Python automatically attaches a reference to __builtins__ inside the globals dictionary if not explicitly suppressed. Consequently, the injected code retains access to functions like open(), import(), and eval() unless custom_globals['__builtins__'] = {} or an alternative mapping is explicitly defined.

Code Injection via AST Manipulation

Unlike plain string evaluation, ast.parse() allows programmatic modification of the syntax tree prior to compilation. When injecting logic into an existing AST:

  • Node Insertion: Developers can insert custom AST nodes (such as ast.Call, ast.Assign, or ast.Expr) into an existing tree using custom ast.NodeTransformer subclasses.
  • Location Metadata Requirement: The Python bytecode compiler requires source positioning metadata (lineno, col_offset, end_lineno, and end_col_offset) on executable nodes. Injected nodes lack this metadata by default. Calling ast.fix_missing_locations(tree) is required before compilation; failing to do so causes compile() to fail with a TypeError or ValueError.
  • Symbol Table Recalculation: The compile() step regenerates the symbol table from scratch based on the final shape of the AST. If an injected node references a variable that does not exist in the enclosing scope, it will be treated as a global variable, potentially throwing a NameError at runtime if undefined.

Runtime Stack and Traceback Mechanics

Code executed from an AST object behaves like standard Python code inside the call stack:

  • Frame Identification: The filename string passed to compile(tree, filename="dynamic_code", mode="exec") appears in tracebacks, debugging tools, and sys._getframe() calls. Specifying a meaningful string facilitates debugging.
  • Line Number Correlation: Tracebacks report errors based on the lineno attributes preserved or fixed on the AST nodes. If injected nodes copy line numbers from original nodes, stack traces point to the source text that originally triggered the injected behavior.

Security and Isolation Limits

Using ast.parse() and compile() does not sandbox execution. A compiled AST produces standard bytecode that executes with the full privileges of the host Python process:

  • Memory and Resource Access: Bytecode instructions can allocate arbitrary amounts of memory, invoke system calls, and access external processes.
  • Introspection Vulnerabilities: Even if __builtins__ is emptied in the global namespace, dynamic code can traverse the object hierarchy through inherited base classes (for example, via object.__subclasses__()) to recover access to modules like os or sys.
  • Static Verification: To safely execute dynamic code using ast.parse(), the AST must be analyzed or whitelisted before calling compile(), verifying that unauthorized node types (e.g., ast.Import, ast.ImportFrom, and dangerous attribute lookups) are strictly prohibited.
