How to Use gc.get_referrers to Debug Memory Leaks

Python relies primarily on reference counting augmented by a cyclic garbage collector to manage memory, but unintended references can prevent objects from being deallocated. When an object that should be destroyed remains in memory, gc.get_referrers() provides a direct way to identify which data structures, frames, or instances are still pointing to it. By inspecting these inbound references, developers can pinpoint the root cause of memory leaks and safely break retention cycles.

Understanding Python's Retention Problem

In CPython, an object's memory is freed immediately when its reference count drops to zero. However, objects frequently linger unexpectedly because they are held by hidden or forgotten references, such as:

  • Module-level global variables or module dictionaries.
  • Long-lived caches (e.g., unbounded dictionaries or functools.lru_cache).
  • Closures capturing variables from an outer scope.
  • Callback registries or event listeners that were never unregistered.
  • Circular references where objects reference each other.

When an object is not collected, the developer needs to trace backward from the target object to see what is keeping it alive.

How gc.get_referrers() Works

The gc module provides an interface to Python’s cyclic garbage collector. The function gc.get_referrers(*objs) takes one or more objects as arguments and returns a list of all objects that directly point to them.

While tools like sys.getrefcount() tell you how many references exist, gc.get_referrers() reveals what those references actually are.

import gc

class TargetNode:
    pass

# Create an instance
node = TargetNode()

# Add to an unexpected persistent container
cache = [node]

# Inspect inbound references
referrers = gc.get_referrers(node)

for ref in referrers:
    print(type(ref), ref)

In this scenario, gc.get_referrers(node) will return the cache list, the local frame or dictionary holding node, and potentially internal tracking structures.

Filtering Noise from Results

When using gc.get_referrers(), the output often includes internal structures that can obscure the actual leak. Common artifacts include:

  1. The Caller’s Frame: The function calling gc.get_referrers() holds a reference to the target via its argument list or local namespace (locals()).
  2. The Result List: If not careful, temporary structures created during debugging can appear as referrers.

To isolate the culprit, filter out namespaces and execution frames:

import gc
import types

def find_leaking_parents(obj):
    referrers = gc.get_referrers(obj)
    actual_holders = []
    
    for ref in referrers:
        # Ignore execution frames and local variable dictionaries
        if isinstance(ref, types.FrameType):
            continue
        if isinstance(ref, dict) and any(v is obj for v in ref.values()):
            # Inspect if this dict belongs to a specific instance or module
            actual_holders.append(ref)
        else:
            actual_holders.append(ref)
            
    return actual_holders

Locating and Fixing the Leak

Once the referencing container or object is identified, resolving the leak involves:

  • Removing the Reference: Explicitly deleting the key from a dictionary, removing an item from a list, or setting an attribute to None.
  • Using Weak References: If an object must be tracked without preventing its collection, replace the strong reference with weakref.ref or use a weakref.WeakValueDictionary.
  • Breaking Cycles: If two objects reference each other and have custom __del__ methods (in older Python versions) or hold onto shared resources, manually sever the connection when the lifecycle ends.
