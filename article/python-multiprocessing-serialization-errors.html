Python Multiprocessing Serialization Errors

When utilizing Python’s multiprocessing module, data sent across process boundaries must be converted into a byte stream via serialization before being transferred over inter-process communication (IPC) channels like pipes and queues. By default, Python relies on the standard pickle protocol for this operation. When an application attempts to pass an unpicklable object—such as an open file descriptor, a lambda, a network socket, or a thread lock—the serialization step fails, triggering specific runtime exceptions that prevent the child process from receiving or processing the task.

The Underlying Serialization Mechanism

Process boundaries in Python do not share an address space. To communicate arguments or state to a child worker, the parent process invokes serialization methods (typically pickle.dumps()) to write data to an underlying IPC buffer, while the child reconstructs the objects via pickle.loads(). If an object cannot be reduced by Python's __reduce__ or copyreg protocols, an exception is raised immediately during the IPC write phase in the parent process, or during reconstruction in the child process.

Primary Serialization Errors

Several distinct exceptions occur depending on the specific unpicklable type being passed:

1. pickle.PicklingError

This is the most direct serialization failure. It occurs when the pickle engine encounters a construct it explicitly does not support, such as closures, dynamically generated classes, or anonymous functions:

  • Lambda functions and closures: _pickle.PicklingError: Can't pickle <function <lambda> at 0x...>: attribute lookup <lambda> on __main__ failed
  • Nested local functions: _pickle.PicklingError: Can't pickle <function outer.<locals>.inner at 0x...>: it's not the same object as outer.<locals>.inner

Because pickle references functions by their fully qualified names rather than by serializing their bytecode, any function defined inside another scope cannot be resolved by name and fails serialization.

2. AttributeError

During multiprocessing, AttributeError commonly surfaces during both serialization and deserialization:

  • Module-level lookup failure: AttributeError: Can't get attribute 'worker_task' on <module '__main__' (built-in)> This typically happens when interactive environments (like Jupyter notebooks) or scripts lacking an if __name__ == '__main__': entry point attempt to run child processes. The child process spawns a fresh interpreter that imports the parent module, but cannot locate the referenced object within the module's namespace.

3. TypeError: cannot pickle '...' object

Operating system handles, thread primitives, and stateful C-extension objects cannot be represented as pure byte streams. Attempting to pass these across processes results in a TypeError:

  • Open file handles: TypeError: cannot pickle '_io.BufferedReader' object
  • Network connections and sockets: TypeError: cannot pickle '_socket.socket' object
  • Thread locks: TypeError: cannot pickle '_thread.lock' object
  • Database sessions: TypeError: cannot pickle 'psycopg2.extensions.connection' object
  • Generators and coroutines: TypeError: cannot pickle 'generator' object

These system-level resources are tied directly to the parent process's memory space and OS-level file descriptor tables, making naive byte-serialization impossible.

How Errors Surface Across Multiprocessing APIs

The manifestation of the error depends on the API utilized:

  • multiprocessing.Process: The error is raised synchronously in the parent process when calling .start() if the start method is set to spawn or forkserver. If using fork (the historic Unix default), the memory space is duplicated without initial serialization; however, attempting to pass unpicklable objects over a multiprocessing.Queue or multiprocessing.Pipe later will raise the exception at the moment of queue.put().
  • multiprocessing.Pool (e.g., pool.map, pool.apply_async): The task and its arguments are immediately queued. If an argument or the target function is unpicklable, the pool worker thread raises the error. When using asynchronous variants like apply_async(), the serialization exception is captured internally and only raised in the parent thread when .get() is called on the resulting AsyncResult object.

Resolution Strategies

To resolve these errors, modify how state is shared between processes:

  • Top-Level Definitions: Define all worker functions, classes, and tasks at the top level of a module rather than inside functions or as lambdas.
  • Defer Resource Initialization: Pass simple serializable configurations (such as file paths, database connection strings, or query parameters) and establish file handles, database connections, and sockets locally inside the child worker's entry function.
  • Alternative Serializers: For complex objects containing closures or dynamically compiled code, employ third-party libraries such as dill or cloudpickle (often integrated via frameworks like multiprocess or pathos), which extend Python’s pickling capabilities to handle code objects and closures.
