Python NamedTemporaryFile Cross-Platform Persistence

Python's tempfile.NamedTemporaryFile provides a way to generate temporary files with accessible filesystem names, but its persistence and file-locking behaviors diverge sharply across operating systems. This article examines how the delete and delete_on_close parameters control file lifecycle, why underlying OS semantics—specifically between POSIX systems and Windows—cause contrasting accessibility behaviors, and how to structure cross-platform code that safely shares and persists temporary files.

The Default Lifecycle and the delete Parameter

By default, tempfile.NamedTemporaryFile(delete=True) creates a file that exists only as long as its file object remains open. The moment the file is closed—either explicitly via .close() or implicitly when exiting a context manager—the file is unlinked and removed from the filesystem.

Setting delete=False disables automated deletion upon closing, delegating lifecycle management to the developer. The file will persist on the filesystem until explicitly removed using os.unlink() or os.remove(). While this behavior is consistent across all platforms, how the file can be accessed while still open depends entirely on the host operating system.

POSIX vs. Windows: File Locking and Re-opening

The primary challenge in cross-platform persistence lies in OS-level file locking semantics when attempting to access the temporary file by its name attribute while it is still open:

  • POSIX (Linux and macOS): File descriptors and filesystem names are loosely coupled. A file opened by NamedTemporaryFile can immediately be reopened by name by another process, thread, or function, even before the original handle is closed. If unlinked while still open, POSIX semantics retain the file data in storage until the last open file descriptor is closed, ensuring stable read/write operations without locking conflicts.
  • Windows: The Windows kernel prevents opening an existing file if another process already holds an open handle without shared read/write/delete permissions. Python's underlying C runtime opens files without the FILE_SHARE_DELETE flag enabled for subsequent opens by name. Consequently, attempting to open a NamedTemporaryFile by its path while it remains open in Python raises a PermissionError.

Cross-Platform Persistence in Python 3.12+

Python 3.12 introduced the delete_on_close parameter to resolve the cross-platform discrepancy. This decouples closing the file handle from deleting the underlying file:

import tempfile
from pathlib import Path

with tempfile.NamedTemporaryFile(delete=True, delete_on_close=False) as temp_file:
    temp_file.write(b"Cross-platform data")
    temp_file.close()  # Closes the handle, releasing Windows locks

    # The file still persists on disk across all OS platforms
    file_path = Path(temp_file.name)
    content = file_path.read_bytes()

# The file is automatically unlinked upon exiting the context manager

By setting delete_on_close=False alongside delete=True, the file descriptor can be closed safely to release platform-specific locks on Windows, while preserving automatic cleanup once the context manager terminates on both Windows and POSIX.

Handling Persistence in Python 3.11 and Earlier

For environments running Python 3.11 or older, achieving cross-platform persistence requires manually managing the lifecycle using delete=False combined with a try...finally block:

import os
import tempfile

temp = tempfile.NamedTemporaryFile(delete=False)
try:
    temp.write(b"Legacy cross-platform data")
    temp.close()  # Handle closed; Windows lock released

    # Safely re-open by name on any OS
    with open(temp.name, "rb") as reader:
        data = reader.read()
finally:
    # Explicit persistence cleanup
    if os.path.exists(temp.name):
        os.unlink(temp.name)

Storage Locations and Durability

Beyond process lifecycles, physical persistence is bound to platform-specific temporary storage locations determined by tempfile.gettempdir():

  • Linux/POSIX: Typically points to /tmp, /var/tmp, or paths defined by environment variables (TMPDIR, TEMP, TMP). In modern Linux distributions, /tmp is often mounted as tmpfs (a volatile, RAM-backed filesystem), meaning files do not survive a system reboot even if delete=False is set.
  • Windows: Defaults to user-specific directories such as C:\Users\<User>\AppData\Local\Temp (via LOCALAPPDATA or TEMP). These paths reside on persistent non-volatile disk storage, persisting across reboots unless pruned by OS storage management utilities.
