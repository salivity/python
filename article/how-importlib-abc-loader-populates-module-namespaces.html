How importlib.abc.Loader Populates Module Namespaces

In Python's import machinery, the importlib.abc.Loader abstract base class governs how source code or bytecode is translated into an active module object. While a finder is responsible for locating the module and returning a ModuleSpec, the loader handles the actual creation, initialization, and execution of that module. This article details the lifecycle of importlib.abc.Loader, explaining how it initializes standard module attributes, binds the module into sys.modules, and executes code inside the module’s namespace dictionary.

The Role of create_module()

When an import request processes a ModuleSpec, the loading phase begins by calling the loader’s create_module(spec) method.

  • Custom Module Objects: If your implementation requires a specialized subclass of types.ModuleType, create_module() must instantiate and return that custom object.
  • Default Behavior: In most implementations, returning None signals to the import system that it should fall back to standard module creation via types.ModuleType(spec.name).

Automatic Namespace Initialization

Before code execution begins, the import system automatically seeds the module’s __dict__ with attributes defined by the spec. Even before exec_module() executes any user code, the following keys are populated:

  • __name__: The fully qualified name of the module.
  • __loader__: A reference to the loader instance managing the import.
  • __package__: The parent package name (or the module name itself if it is a package).
  • __spec__: The ModuleSpec instance associated with this module.
  • __file__: The physical path to the module source, if applicable.
  • __cached__: The path to the compiled bytecode, if supported.

Insertion into sys.modules

Python inserts the newly created, partially initialized module into sys.modules prior to executing its code. This step is critical because it prevents infinite recursion and crashes caused by circular imports. If a module imports another module that imports the original module back, the secondary import retrieves the incomplete module directly from sys.modules rather than triggering a redundant load sequence.

Code Execution via exec_module()

The primary responsibility of importlib.abc.Loader is implemented inside exec_module(module). Once the module exists and sits in sys.modules, exec_module() performs the following sequence:

  1. Retrieving Source or Bytecode: The loader fetches the raw payload, typically reading text from disk, a database, or a network endpoint.
  2. Compiling: If working with raw source, the loader passes the text to Python's built-in compile() function, generating a code object in 'exec' mode.
  3. Executing within the Namespace: The loader calls Python’s built-in exec() function, passing the code object along with the module’s __dict__: 
    exec(code_object, module.__dict__)

Because module.__dict__ serves as both the global and local namespace during this call, any top-level variable assignment, function definition (def), class declaration (class), or imported dependency inside the executed code directly mutates the dictionary. Once exec() finishes, module.__dict__ contains all declared symbols, completing the module population process.
