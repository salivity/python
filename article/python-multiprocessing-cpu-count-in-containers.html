Python multiprocessing.cpu_count in Containers

In containerized environments such as Docker and Kubernetes, Python's multiprocessing.cpu_count() often reports inaccurate core counts by querying the physical host rather than the container's assigned limits. This article explains the internal mechanisms Python uses to detect CPUs, why these mechanisms fail to account for container resource constraints, the performance risks involved, and how to reliably determine actual core availability.

How multiprocessing.cpu_count() Works

Under the hood, multiprocessing.cpu_count() is an alias for os.cpu_count(). On Linux systems, this function relies on standard POSIX C library calls, specifically:

sysconf(_SC_NPROCESSORS_ONLN);

This system call queries the Linux kernel to determine the number of physical or logical CPU cores currently online and available to the operating system kernel. It does not inspect user-space process limits, virtualization boundaries, or control group configurations.

Why Container Limits Are Ignored

Containers are not virtual machines; they share the host kernel. Resource restrictions in containers are enforced via Linux Control Groups (cgroups), specifically through two main mechanisms:

  1. Completely Fair Scheduler (CFS) Quotas: When you allocate fractional or fixed CPUs (e.g., --cpus="2.0" in Docker or resources.limits.cpu: "2" in Kubernetes), the kernel does not hide host cores. Instead, it enforces a time quota over a period (typically 100ms). If a container has a 2-core limit, it is granted 200ms of CPU time across every 100ms window.
  2. CPU Pinning (cpuset): When you explicitly assign cores (e.g., --cpuset-cpus="0,1"), the kernel restricts the container processes to run only on designated physical cores.

Because sysconf(_SC_NPROCESSORS_ONLN) only checks total online host cores, multiprocessing.cpu_count() completely ignores CFS quotas. For example, if a container runs on a 64-core host but is limited to 2 CPUs via Kubernetes, multiprocessing.cpu_count() will still return 64.

Consequences of Inaccurate Core Detection

Assuming host-level core counts inside a constrained container leads to severe performance degradation:

  • Excessive Worker Spawning: Libraries like Celery, Gunicorn, or data-processing frameworks default their worker pools to multiprocessing.cpu_count(). A container restricted to 2 cores might spawn 64 or 128 workers.
  • CPU Throttling: Spawning dozens of threads or processes competing for limited CFS runtime causes aggressive kernel throttling, where processes are repeatedly paused mid-execution.
  • Context Switching Overhead: The CPU spends significant time switching execution contexts rather than executing instructions.
  • Out-Of-Memory (OOM) Errors: More processes consume more baseline memory, increasing the likelihood that the container exceeds its memory limit and gets terminated by the Linux OOM killer.

Handling cpuset vs. CFS Quota

If a container uses CPU pinning (cpuset), Python's os.sched_getaffinity(0) can detect the assigned cores:

import os

# Returns the number of pinned cores if cpuset is applied
available_cpus = len(os.sched_getaffinity(0))

However, if the container uses CFS quotas (which is the standard implementation in Kubernetes and most Docker deployments), os.sched_getaffinity(0) still returns the total host count.

Correctly Determining CPU Availability

To accurately find available compute capacity, applications must read the container's cgroup configuration files directly.

For cgroups v1:

CFS quota settings reside in /sys/fs/cgroup/cpu/:

  • cpu.cfs_quota_us: The allowed run time in microseconds per period (returns -1 if unlimited).
  • cpu.cfs_period_us: The length of the period in microseconds (typically 100000).

For cgroups v2:

Settings reside in /sys/fs/cgroup/cpu.max:

  • Contains two values: quota and period (e.g., 200000 100000 for 2 cores, or max 100000 if unlimited).

Implementation Example:

import math
import os
from pathlib import Path

def get_container_cpu_limit():
    # 1. Check cgroups v2
    cgroup_v2 = Path("/sys/fs/cgroup/cpu.max")
    if cgroup_v2.exists():
        quota, period = cgroup_v2.read_text().split()
        if quota != "max":
            return math.ceil(int(quota) / int(period))

    # 2. Check cgroups v1
    quota_v1 = Path("/sys/fs/cgroup/cpu/cpu.cfs_quota_us")
    period_v1 = Path("/sys/fs/cgroup/cpu/cpu.cfs_period_us")
    if quota_v1.exists() and period_v1.exists():
        quota = int(quota_v1.read_text().strip())
        period = int(period_v1.read_text().strip())
        if quota > 0:
            return math.ceil(quota / period)

    # 3. Fallback to process affinity (e.g., cpuset)
    if hasattr(os, "sched_getaffinity"):
        return len(os.sched_getaffinity(0))

    # 4. Final fallback to host CPU count
    return os.cpu_count()

Improvements in Python 3.13

Recognizing this common issue, Python 3.13 introduced os.process_cpu_count(). Unlike os.cpu_count() and multiprocessing.cpu_count(), os.process_cpu_count() is designed to return the number of logical CPUs that the calling process is restricted to, taking into account thread affinity and system limits where supported by the platform.
