How itertools.product Computes Cartesian Products

In Python, computing the Cartesian product of an arbitrary number of iterables dynamically cannot be achieved using standard nested for loops without awkward recursive patterns or code generation. The itertools.product() function solves this by managing state through an internal flat array of indices that behaves like an odometer, advancing through combinations sequentially. This article examines the internal mechanics of itertools.product(), detailing how it caches inputs into memory pools, tracks coordinate states, and yields elements without relying on nested execution frames.

The Limitation of Static Nested Loops

A standard Cartesian product of two lists can be written simply:

result = [(x, y) for x in list_a for y in list_b]

However, if the number of input iterables is determined at runtime, the required nesting depth is unknown. Writing variable-depth loops in pure Python requires either recursive generator functions, which introduce call-stack overhead, or dynamic code evaluation (exec), which is slow and unsafe.

Step 1: Pre-Caching Inputs into Pools

Before yielding any combinations, itertools.product(*iterables, repeat=1) consumes all provided iterables and stores their elements inside tuple pools in memory.

If the repeat keyword argument is used, it repeats the references to these pools accordingly. Because iterators in Python can be one-time streams (such as generators or file handles), caching them into fixed tuples is required so that inner dimensions can be traversed repeatedly from index zero. If any input iterable is empty, itertools.product() terminates immediately without yielding anything.

Step 2: The Odometer Pattern (Index Tracking)

Instead of nesting loops, itertools.product() maintains a single, flat C-array of integer indices representing the current position within each pool.

For example, given three pools of lengths 2, 3, and 2:

  • Initial indices: [0, 0, 0]
  • First advance: [0, 0, 1]
  • Second advance: the last index overflows its pool length (2), resets to 0, and carries 1 to the adjacent index: [0, 1, 0]

This design mimics an odometer or positional number system with mixed radix bases, where each digit position has a base equal to the length of its corresponding pool.

Python Representation of the Internal Logic

In CPython, this is written in optimized C (itertoolsmodule.c), but the core algorithmic execution operates conceptually as follows:

def conceptual_product(*args, repeat=1):
    pools = [tuple(pool) for pool in args] * repeat
    n = len(pools)
    if any(len(p) == 0 for p in pools):
        return

    # Track the current index in each pool
    indices = [0] * n
    
    # Yield the first combination
    yield tuple(pools[i][indices[i]] for i in range(n))

    while True:
        # Advance from the rightmost pool backwards
        for i in reversed(range(n)):
            if indices[i] + 1 < len(pools[i]):
                indices[i] += 1
                break
            else:
                indices[i] = 0
        else:
            # If the loop finished without breaking, all positions overflowed
            return
            
        yield tuple(pools[i][indices[i]] for i in range(n))

Carry-Over and Termination

The generator evaluates indices from right to left:

  1. It attempts to increment the index of the rightmost pool.
  2. If that index exceeds the pool's bounds, it wraps back to 0, and the loop moves leftward to increment the next pool's index.
  3. Once an index is successfully incremented without overflow, the cycle breaks, and a new tuple is yielded.
  4. If the carry-over propagates past the leftmost pool (index 0), every possible combination has been exhausted, and the generator halts.

Efficiency and Complexity

Because itertools.product() executes entirely in compiled C:

  • Memory Overhead: Beyond the initial memory required to store the input tuples, the auxiliary memory complexity is \(O(N)\), where \(N\) is the number of iterables. It does not load the full product into memory, generating each item on demand.
  • CPU Overhead: It avoids the overhead of Python bytecode execution and recursive call stack allocation. Advancing indices and slicing tuples are executed via direct pointer arithmetic and C-level array indexing.
