Python Event Loop: Waking Up Suspended Async Tasks

In Python's asyncio, asynchronous tasks pause execution at await expressions, yielding control back to the central event loop. This article details the low-level mechanics of how the event loop registers callbacks, monitors operating system notifications, and ultimately wakes up and resumes suspended coroutines when their operations complete.

Coroutines, Tasks, and the Role of Futures

When a coroutine yields control via await, it typically awaits a Task or a lower-level Future object. A Future acts as an empty container for a result that has not yet been computed.

When a task awaits a future, it registers its own resumption method—internally referred to as Task._step()—as a callback on that future using the Future.add_done_callback() method. The coroutine then suspends execution, unrolling its call stack and returning execution directly to the event loop's main iteration cycle.

The I/O Selector Bridge

To handle asynchronous network and disk I/O, the Python event loop relies on the standard library's selectors module. Depending on the operating system, this module abstracts high-performance I/O multiplexing primitives such as epoll on Linux, kqueue on macOS/BSD, or I/O Completion Ports (IOCP) on Windows.

When an operation requires waiting for a socket (for example, reading data from an incoming network stream):

  1. The event loop creates a Future for the operation.
  2. The loop registers the socket's underlying file descriptor with the OS selector, configuring it to trigger on specific events (such as read or write readiness).
  3. The event loop associates an internal callback handler with that file descriptor registration.

The Polling and Notification Cycle

The event loop continuously cycles through an execution loop. When there are no tasks actively running, the loop calls selector.select(timeout). This call blocks until one of two conditions occurs:

  • The specified timeout expires (often calculated based on the next scheduled timer or sleep event).
  • The operating system signals that one or more registered file descriptors are ready for I/O.

Once the kernel signals readiness, select() unblocks and returns a list of ready file descriptors along with their associated internal event loop callbacks.

Triggering the Wake-up Pipeline

Once the event loop receives notification that an I/O event is ready, it initiates a sequential chain of callbacks to resume the task:

  1. Execute I/O Callback: The event loop calls the handler mapped to the ready file descriptor. This handler performs the actual non-blocking read or write operation on the socket.
  2. Resolve the Future: Upon successfully receiving data or finishing the operation, the handler calls future.set_result(data) on the associated Future.
  3. Execute Done Callbacks: Setting the result automatically triggers all callbacks attached to the future via add_done_callback(). Among these callbacks is the suspended task’s _step() method.
  4. Queue Task for Resumption: Rather than executing the task immediately within the I/O callback, Task._step() places itself onto the event loop’s internal _ready FIFO queue.

Resuming Coroutine Execution

In the next iteration of the loop, the event loop pops items from the _ready queue. When the task's turn arrives, the loop invokes Task._step().

Under the hood, this method calls coroutine.send(result), passing the resolved future's data directly into the coroutine. Python's generator mechanism resumes the coroutine at the exact bytecode instruction following the await keyword, allowing the program to continue executing seamlessly until it either finishes or hits another suspension point.
