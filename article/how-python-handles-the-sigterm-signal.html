How Python Handles the SIGTERM Signal

When an operating system sends a SIGTERM (Signal Terminate) to an active Python script, the behavior depends on whether the script has registered a custom handler or relies on the interpreter's default settings. This article covers how the operating system kernel communicates with the Python virtual machine, why default termination skips Python cleanup code, and the step-by-step mechanism the interpreter uses to execute signal handlers safely on the main thread.

The Default Behavior: Immediate Termination

By default, Python inherits the standard operating system disposition for SIGTERM, which is SIG_DFL (default action: terminate the process).

When the OS sends SIGTERM to an unconfigured Python process:

  • The kernel halts the process immediately.
  • The operating system reclaims allocated memory, open file descriptors, and network sockets.
  • Python-level cleanup routines do not run. Any active try...finally blocks, context managers (with statements), and callbacks registered with the atexit module are bypassed completely.

The Signal Delivery Mechanism

Operating system signals are asynchronous, but Python code execution requires a coherent runtime state. To prevent state corruption, Python handles signals using a two-stage mechanism:

  1. The C-Level Handler: When the signal arrives, the kernel interrupts the process and executes Python’s low-level C runtime signal handler. This C handler does not execute your Python code directly. Instead, it marks a flag in the interpreter state indicating that a signal has arrived, then immediately returns control to the operating system.
  2. Bytecode Check (The Evaluation Loop): The Python virtual machine checks this signal flag at regular intervals—specifically, between bytecode instructions.
  3. Execution on the Main Thread: Once the interpreter detects the set flag, it calls the corresponding Python signal handler. Signal handlers in Python always execute synchronously on the main thread, regardless of which thread originally received the OS-level signal.

Handling SIGTERM Gracefully

To prevent sudden shutdown and allow graceful resource cleanup, a script must intercept SIGTERM explicitly using the built-in signal module:

import signal
import sys
import time

def handle_sigterm(signum, frame):
    # Raising SystemExit allows Python to run cleanup routines
    sys.exit(0)

signal.signal(signal.SIGTERM, handle_sigterm)

try:
    while True:
        time.sleep(1)
finally:
    print("Cleanup logic executed successfully.")

When a custom handler catches SIGTERM:

  • The main thread stops executing normal bytecode and invokes the handler function.
  • If the handler raises SystemExit (via sys.exit()), Python initiates standard exception unwinding.
  • try...finally blocks execute, context managers invoke their __exit__ methods, and atexit handlers run before the process exits.

Edge Cases and Complications

Two primary conditions affect how quickly a Python script responds to a SIGTERM:

  • Blocking C Extensions: If Python is waiting inside an external C library or a non-interruptible system call, the interpreter cannot inspect its internal signal flags. The custom signal handler will not run until the external call returns control to the Python evaluation loop.
  • Multithreading: Because signal handlers only execute on the main thread, the main thread must remain unblocked and capable of processing interpreter events. If the main thread is deadlocked or permanently blocked on a thread join, it will never process the pending SIGTERM flag.
