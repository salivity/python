How Python Validates Keyword Arguments at Parse Time

This article explains how Python checks keyword arguments during parsing, focusing on grammar rules and identifier validation. While Python is a dynamic language that binds arguments to function parameters at runtime, its parser enforces strict syntactic constraints on keyword arguments before code execution occurs. Understanding this mechanism clarifies what gets caught at compile time as a SyntaxError versus what defers to runtime as a TypeError.

The Role of the Grammar Specification

Python’s parser operates on a formal grammar—implemented via a Parsing Expression Grammar (PEG) parser in Python 3.9 and newer. At parse time, the parser has no knowledge of the target function's definition, its signature, or whether the invoked callable actually accepts the specified parameters. Instead, parse-time validation strictly ensures that explicit keyword arguments adhere to the formal definition of Python identifiers and valid call structures.

In Python’s PEG grammar, function call arguments follow strict structural rules:

kwargs:
    | ','.kwarg_or_starred+ ','?
kwarg_or_starred:
    | NAME '=' expression 
    | '*' expression 
    | '**' expression

The key component in this rule is the NAME token on the left-hand side of the = operator.

Lexical Analysis and the NAME Token

Before grammar rules are evaluated, the lexer (tokenizer) reads the raw source code and converts characters into tokens. For an explicit keyword argument to be syntactically valid:

  1. Identifier Syntax: The left side of the assignment must match the NAME token pattern. Under PEP 3131, Python identifiers must begin with an underscore or a character with the Unicode category "Letter" (Lu, Ll, Lt, Lm, Lo, or Nl), followed by letters, digits, or underscores.
  2. Rejection of Literals and Expressions: If a developer attempts to pass an argument name as a string literal (e.g., func("param"=value)), a number (e.g., func(1=value)), or an expression (e.g., func(a.b=value)), the tokenizer produces tokens other than NAME (such as STRING, NUMBER, or an attribute access sequence).

Because the grammar rule kwarg_or_starred explicitly demands a NAME token immediately preceding the = token, encountering any other token type causes an immediate parse failure, emitting a SyntaxError.

Sequence and Positioning Enforcement

The parser also validates parameter ordering conventions:

  • Keyword Arguments After Positional Arguments: The grammar disallows standard positional arguments from following explicit keyword arguments. A sequence like func(x=1, 2) violates the argument ordering rules defined in the grammar and triggers a SyntaxError: positional argument follows keyword argument.
  • Duplicate Explicit Names: While early parsing constructs the Abstract Syntax Tree (AST), the AST compiler also traverses call nodes to check for duplicate explicit keyword names (such as func(a=1, a=2)), raising a SyntaxError: keyword argument repeated prior to bytecode emission.

Parse-Time vs. Runtime Boundary

Parse-time validation is strictly structural. Python cannot verify at parse time whether a keyword argument matches the parameter list defined in def func(...), because functions can be dynamically redefined, decorated, or passed as first-class objects.

Consequently, the following distinctions apply:

  • Checked at Parse Time: Whether the keyword name is a valid identifier (NAME), whether positional arguments follow keywords, and whether identical explicit keyword names are repeated.
  • Deferred to Runtime: Whether the keyword name exists on the function signature, whether required positional arguments are satisfied, and whether dynamically unpacked dictionary keys (**kwargs) contain valid parameter names. Dynamic dictionary keys that are not valid Python identifiers bypass parse-time checks entirely and fail with a TypeError during call execution.
