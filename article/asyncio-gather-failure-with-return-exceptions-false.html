asyncio.gather Failure with return_exceptions=False

When using asyncio.gather() in Python with the default return_exceptions=False configuration, a failure in any individual task immediately propagates that exception to the caller awaiting the gather call. While the caller receives the exception immediately, the remaining sibling tasks are not automatically cancelled; they continue executing in the background, which can lead to unexpected side effects or unhandled exceptions.

Immediate Exception Propagation

By default, return_exceptions is set to False. When multiple coroutines or tasks are scheduled via asyncio.gather(), the event loop executes them concurrently. If one of these tasks encounters an error and raises an exception:

  1. The asyncio.gather() call stops waiting and immediately re-raises that specific exception at the await point.
  2. The calling code must handle the exception via a standard try...except block, or the program will terminate with a traceback.
  3. The return values of any tasks that completed prior to or after the failure are lost to the caller of gather().
import asyncio

async def failing_task():
    await asyncio.sleep(0.1)
    raise ValueError("Something went wrong!")

async def slow_task():
    await asyncio.sleep(0.5)
    print("Slow task finished successfully.")

async def main():
    try:
        await asyncio.gather(
            failing_task(),
            slow_task(),
            return_exceptions=False
        )
    except ValueError as e:
        print(f"Caught exception: {e}")
    
    # Wait to demonstrate slow_task is still running
    await asyncio.sleep(1)

asyncio.run(main())

The Sibling Tasks Keep Running

The most critical nuance of return_exceptions=False is task cancellation—or the lack thereof. When asyncio.gather() raises an exception:

  • No Automatic Cancellation: The other tasks passed to gather() are not cancelled automatically. They continue their execution in the event loop until they naturally complete or fail.
  • Leaked Operations: If a sibling task performs network I/O, database writes, or heavy computation, it will consume system resources despite the caller having already moved on due to the error.
  • Subsequent Exceptions: If other sibling tasks also raise exceptions after the first failure, those subsequent exceptions cannot be caught by the original gather() call. Instead, the event loop will trigger a "Task exception was never retrieved" warning in the logs.

Alternatives and Best Practices

To avoid orphaned background tasks when dealing with concurrent failures, consider the following alternatives:

  • Explicit Cancellation: Catch the exception, inspect pending tasks, and explicitly call task.cancel() on any unfinished tasks.
  • return_exceptions=True: Setting this flag suppresses immediate propagation. Instead, asyncio.gather() waits for all tasks to complete and returns a list containing both successful return values and the raised Exception objects for manual inspection.
  • asyncio.TaskGroup (Python 3.11+): The modern standard for structured concurrency. If any task inside a TaskGroup raises an exception, the remaining tasks inside the group are automatically cancelled, preventing dangling background execution.
