How typing.final Enforces Final Methods in Python

The typing.final decorator, introduced in Python 3.8 via PEP 591, is designed to indicate that a method should not be overridden by subclasses or that a class should not be inherited. This article explains the underlying mechanism of typing.final, distinguishing between static analysis enforcement and runtime behavior, and demonstrates how Python tooling uses it to prevent method overriding.

Static Enforcement via Type Checkers

Python is a dynamically typed language that relies heavily on conventions rather than strict compiler-enforced restrictions. Consequently, typing.final does not prevent method overriding at runtime. Instead, it enforces constraints during static analysis.

Static type checkers such as Mypy, Pyright, and integrated development environment (IDE) analyzers inspect source code before execution. When a method is marked with the @final decorator, the type checker flags any subclass attempting to redefine that method as an error.

from typing import final

class BaseService:
    @final
    def calculate_metrics(self) -> None:
        print("Calculating core metrics.")

class CustomService(BaseService):
    def calculate_metrics(self) -> None:  # Static type checker raises an error here
        print("Overriding metrics.")

Running a static type checker like Mypy against this code results in an explicit violation:

error: Cannot override final attribute "calculate_metrics" (previously declared in base class "BaseService")

Runtime Behavior

At runtime, the @final decorator acts primarily as an identity function. In CPython's standard library implementation, the decorator simply attaches an internal __final__ = True attribute to the function or class and returns it unchanged.

Because Python's method resolution order (MRO) and class creation processes remain unaffected by the decorator, the Python interpreter will execute overridden methods without raising a native exception:

service = CustomService()
service.calculate_metrics()  # Prints: "Overriding metrics." (No runtime exception)

Because the runtime permits this behavior, continuous integration (CI) pipelines must incorporate static analysis steps (such as mypy or pyright) to guarantee that @final constraints are actively enforced across a codebase.

Strict Runtime Enforcement Alternative

If a project requires strict runtime rejection of method overrides rather than relying solely on static analysis, developers must implement a custom metaclass. By inspecting the class dictionary during the class creation phase (__init_subclass__ or metaclass.__new__), a program can dynamically verify if a child class redefines any attribute marked with __final__.

class StrictFinalMeta(type):
    def __init__(cls, name, bases, namespace):
        super().__init__(name, bases, namespace)
        for base in bases:
            for attr_name, attr_val in namespace.items():
                base_attr = getattr(base, attr_name, None)
                if base_attr and getattr(base_attr, "__final__", False):
                    raise RuntimeError(f"Cannot override final method '{attr_name}' in class '{name}'")

class SecureBase(metaclass=StrictFinalMeta):
    @final
    def execute(self):
        pass

class Breach(SecureBase):
    def execute(self):  # Raises RuntimeError at import/definition time
        pass

Summary

The standard typing.final decorator enforces method immutability strictly through static type systems. It signals developer intent, enables IDE safety checks, and prevents architectural drift via static verification, leaving runtime execution lightweight and free from overhead.
