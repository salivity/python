Python MethodWrapperType vs User-Defined Methods

In Python, types.MethodWrapperType represents a bound method-wrapper for C-implemented special methods, whereas standard user-defined methods are represented by types.MethodType. While both represent callable methods bound to an instance, their origins, internal representations, introspection capabilities, and performance behaviors differ significantly based on whether the underlying routine is a C-level slot or Python bytecode.

Underlying Origin and Creation

The primary distinction lies in what the method wraps.

  • User-Defined Methods (types.MethodType): When you define a function inside a class using Python syntax (def func(self): ...), Python creates a function object. Accessing this function through an instance invokes its descriptor protocol (__get__), producing an instance of types.MethodType that binds the function to the instance.
  • Method-Wrappers (types.MethodWrapperType): Built-in and C-extension types implement core behaviors (like __repr__, __add__, or __len__) as C-level function pointers stored in type slots. Accessing one of these dunder methods on an instance (for example, [].__repr__ or (42).__add__) invokes the __get__ descriptor of a wrapper_descriptor. This produces a method-wrapper, represented by types.MethodWrapperType.

Introspection and Python-Level Attributes

Because user-defined methods wrap native Python function objects, they expose the full suite of Python execution metadata:

  • method.__code__: Contains the bytecode, variable names, and line numbers.
  • method.__globals__: The global namespace of the module where the function was defined.
  • method.__closure__: Cell variables if the method closes over outer scopes.

In contrast, types.MethodWrapperType points directly to compiled C functions and lacks these attributes entirely. Inspecting a MethodWrapperType instance yields C-level wrapper descriptors instead:

  • __self__: The instance to which the wrapper is bound (shared with MethodType).
  • __objclass__: The class that defines the underlying slot wrapper (e.g., list, int, or object).
  • It does not possess __code__, __globals__, or __annotations__. Attempting to access these attributes raises an AttributeError.

Descriptor Binding Mechanics

The descriptor chain that creates each type is fundamentally different:

  1. User Method Resolution: instance.method \(\rightarrow\) Class.__dict__['method'].__get__(instance, Class) \(\rightarrow\) returns types.MethodType(Class.__dict__['method'], instance)

  2. Slot Wrapper Resolution: instance.__dunder__ \(\rightarrow\) Class.__dict__['__dunder__'].__get__(instance, Class) \(\rightarrow\) returns a method-wrapper (types.MethodWrapperType) wrapping the slot pointer.

If a user class overrides a dunder method in pure Python:

class Custom:
    def __str__(self):
        return "custom"

Accessing Custom().__str__ will return a types.MethodType, not a types.MethodWrapperType. The wrapper type only emerges when binding to a dunder method implemented in C on the type's underlying C struct.

Execution Overhead

types.MethodWrapperType bypasses the standard Python bytecode evaluation loop when called. Invoking a method-wrapper directly executes the C-level function pointer associated with that type's slot, providing faster execution and smaller memory overhead per call compared to the evaluation of a standard Python stack frame in types.MethodType.
