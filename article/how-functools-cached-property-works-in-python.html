How functools.cached_property Works in Python

The functools.cached_property decorator, introduced in Python 3.8, transforms a class method into a property whose value is computed once and then cached as a standard attribute for the lifetime of the instance. This article explains how the underlying descriptor protocol operates, why mutating the instance dictionary allows the cache to function, how it compares to the standard @property, and how to manually invalidate or clear cached values.

The Problem It Solves

When working with object-oriented Python, you often encounter properties that require expensive operations, such as querying a database, parsing large files, or running heavy mathematical calculations. Using a regular @property re-runs the method every time the attribute is accessed:

class DataAnalyzer:

    def __init__(self, dataset):
        self.dataset = dataset

    @property
    def summary(self):
        # Recomputed on every call to instance.summary
        return sum(self.dataset) / len(self.dataset)

While you could manually store the result in an instance variable with an if self._summary is None check, functools.cached_property provides a clean, built-in solution that handles this caching automatically.

The Mechanics: Non-Data Descriptors

To understand how cached_property works, you must look at Python's descriptor protocol and attribute lookup order.

Python attributes can be descriptors if they implement methods like __get__, __set__, or __delete__:

  • Data Descriptors implement both __get__ and __set__ (or __delete__). They take precedence over an instance's __dict__.
  • Non-Data Descriptors implement only __get__. An entry in the instance's __dict__ takes precedence over a non-data descriptor.

The functools.cached_property class is implemented as a non-data descriptor. Here is the step-by-step lifecycle of an attribute lookup:

  1. First Access: When you call instance.expensive_attribute for the first time, Python checks instance.__dict__. Because the attribute does not yet exist there, Python falls back to the class attribute, finding the cached_property non-data descriptor and invoking its __get__ method.

  2. Computation and Storage: Inside __get__, the decorator calls the underlying wrapped function with instance as its sole argument. It takes the returned result and explicitly sets it in the instance's dictionary:

    instance.__dict__[self.attrname] = val

  3. Subsequent Accesses: On all future calls to instance.expensive_attribute, Python inspects instance.__dict__ first. Because the key is now present in the dictionary, Python returns the cached value directly without ever invoking __get__ or running the underlying method again.

Because subsequent lookups become simple dictionary reads, access speed is identical to accessing any standard instance attribute.

Code Example

import time
from functools import cached_property


class ReportGenerator:

    def __init__(self, raw_data):
        self.raw_data = raw_data

    @cached_property
    def processed_report(self):
        print("Running heavy computation...")
        time.sleep(2)  # Simulating an expensive task
        return [x * 2 for x in self.raw_data]


report = ReportGenerator([1, 2, 3])

# First call: Computes and caches
print(report.processed_report)
# Output:
# Running heavy computation...
# [2, 4, 6]

# Second call: Fetched directly from report.__dict__
print(report.processed_report)
# Output:
# [2, 4, 6]

Cache Invalidation

Because the cached result is stored directly inside instance.__dict__, invalidating or clearing the cache is straightforward: delete the attribute using the del statement.

# Clear the cache
del report.processed_report

# Accessing it again forces a recomputation
print(report.processed_report)
# Output:
# Running heavy computation...
# [2, 4, 6]

Deleting the key from report.__dict__ restores the original state where the attribute is missing from the instance dictionary, prompting Python to invoke the descriptor's __get__ method on the next access.

Key Considerations and Limitations

  • Instances Must Have __dict__: cached_property relies entirely on mutating the instance dictionary. Consequently, it does not work on classes using __slots__ unless __dict__ is explicitly included in the __slots__ declaration.
  • Thread Safety: In Python versions prior to 3.12, cached_property did not employ locking during the initial calculation, meaning concurrent threads could execute the computation multiple times simultaneously. Python 3.12 introduced locking mechanisms to ensure the computation runs only once across multiple threads.
  • Mutability: The cache stores a reference to the returned object. If the returned object is mutable (such as a list or a dictionary) and modified elsewhere, those modifications persist in the cache.
