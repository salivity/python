Python sys.excepthook Global Exception Handling

This article explores Python's sys.excepthook mechanism, which acts as the language's last line of defense for unhandled exceptions. By reading this guide, you will understand how Python natively processes uncaught runtime errors, how to intercept them globally by overriding sys.excepthook, how to maintain the original traceback behavior, and how to address modern multithreading considerations.

How Python Processes Unhandled Exceptions

When an exception is raised in a Python application and is not caught by any try...except block, the interpreter does not immediately terminate silently. Instead, it looks up the callable assigned to sys.excepthook and invokes it, passing three key arguments:

  1. exc_type: The class of the exception that was raised (e.g., ValueError, ZeroDivisionError).
  2. exc_value: The actual instance of the exception containing the error message and attributes.
  3. exc_traceback: A traceback object encapsulating the call stack at the point where the error occurred.

By default, Python sets sys.excepthook to an internal implementation (sys.__excepthook__) that formats these three arguments and prints the standard traceback to sys.stderr before terminating the execution.

Defining a Custom Global Exception Handler

Developers can override sys.excepthook by reassigning it to any custom callable that accepts the three expected positional arguments. This enables centralized operations such as writing crash dumps, logging unhandled errors to external monitoring platforms (like Sentry or Datadog), or alerting operations teams before process shutdown.

import sys
import logging

logging.basicConfig(filename="app_errors.log", level=logging.ERROR)

def custom_exception_handler(exc_type, exc_value, exc_traceback):
    # Ignore KeyboardInterrupt so the user can still terminate the script with Ctrl+C
    if issubclass(exc_type, KeyboardInterrupt):
        sys.__excepthook__(exc_type, exc_value, exc_traceback)
        return

    # Log the unhandled error with the complete traceback
    logging.critical("Uncaught exception occurred", exc_info=(exc_type, exc_value, exc_traceback))

# Assign the custom function to sys.excepthook
sys.excepthook = custom_exception_handler

Preserving Default Behavior with sys.__excepthook__

When writing a custom hook, developers often want to perform a secondary action (such as writing to a log file or displaying a GUI error dialog) while still outputting the standard traceback to the console. Python preserves the original system handler in sys.__excepthook__. Invoking sys.__excepthook__(exc_type, exc_value, exc_traceback) inside your custom hook ensures standard console output is not suppressed unless explicitly desired.

Multi-Threading Considerations

A critical limitation of sys.excepthook is that it only catches unhandled exceptions originating from the main thread. If an uncaught exception occurs inside a worker thread created via the threading module, sys.excepthook will not intercept it.

To address this, Python 3.8 introduced threading.excepthook. It accepts a single argument—an ExceptHookArgs named tuple containing exc_type, exc_value, exc_traceback, and thread. For complete application-wide global coverage across all threads in modern Python, both hooks should be defined:

import threading

def custom_thread_exception_handler(args):
    custom_exception_handler(args.exc_type, args.exc_value, args.exc_traceback)

threading.excepthook = custom_thread_exception_handler

By configuring both sys.excepthook and threading.excepthook, applications gain a predictable, centralized pipeline to handle unexpected failures without scattering repetitive error-handling boilerplate throughout the codebase.
