Understanding Python yield from Delegation

The yield from expression in Python provides a transparent delegation mechanism that connects a caller directly to a subgenerator. Introduced in PEP 380, it serves two critical purposes: it simplifies the consumption of iterables by eliminating boilerplate loops, and it establishes a direct, bidirectional communication channel between the delegating generator's caller and the underlying subgenerator. This allows data, exceptions, and return values to flow seamlessly across the generator stack without manual forwarding.

Delegating Iteration

At its most basic level, yield from acts as an automated pipeline for yielding values from an iterable or another generator. In earlier versions of Python, delegating to an iterable required an explicit loop:

def manual_delegation(iterable):
    for item in iterable:
        yield item

With yield from, this simplifies to:

def delegator(iterable):
    yield from iterable

Beyond cleaner syntax, yield from optimizes performance at the C level and maintains a live connection to the underlying subgenerator instead of merely unpacking values sequentially.

Bidirectional Communication with .send()

The true power of yield from lies in bidirectional data transfer. When a generator is paused at a yield from statement, sending a value into the delegator via the .send() method forwards that value directly into the subgenerator's active yield expression.

def subgenerator():
    received = yield "Ready"
    yield f"Processed: {received}"

def delegator():
    yield from subgenerator()

gen = delegator()
print(next(gen))        # Outputs: Ready
print(gen.send("Data")) # Outputs: Processed: Data

In this flow:

  1. next(gen) advances the subgenerator to its first yield point (yield "Ready"), returning "Ready" up to the caller.
  2. gen.send("Data") injects "Data" directly into the subgenerator, binding it to the received variable.
  3. The delegating generator remains a transparent conduit throughout the process, unaware of the specific value being transferred.

Forwarding Exceptions with .throw() and .close()

Bidirectional delegation also encompasses lifecycle control and exception handling. When a caller invokes .throw() or .close() on the delegator, those actions are forwarded to the subgenerator:

  • .throw(ExceptionType, value): The exception is raised inside the subgenerator at its current suspension point. If the subgenerator catches and handles the exception, it can continue executing and yield another value back to the caller. If the subgenerator does not handle it, the exception bubbles up through the delegator.
  • .close(): A GeneratorExit exception is raised inside the subgenerator. If the subgenerator was delegated via yield from, it cleans up its resources properly before the delegator itself terminates.

Capturing Subgenerator Return Values

Prior to yield from, returning a value from a generator was either invalid syntax or required catching the StopIteration exception manually, as a generator's return expr attaches the value to the StopIteration.value attribute.

yield from handles this automatically by assigning the subgenerator’s final return value directly to a variable in the delegator:

def average_collector():
    total = 0
    count = 0
    while True:
        val = yield
        if val is None:
            break
        total += val
        count += 1
    return total / count if count else 0

def delegator():
    # The return value of average_collector is assigned to avg
    avg = yield from average_collector()
    yield f"Final Average: {avg}"

calc = delegator()
next(calc)         # Prime the generator
calc.send(10)
calc.send(20)
calc.send(30)
try:
    calc.send(None) # Signals the subgenerator to break and return
except StopIteration:
    pass

When average_collector executes return, it raises a StopIteration carrying the computed average. The yield from mechanism intercepts this exception, extracts StopIteration.value, assigns it to avg, and resumes execution in delegator.
