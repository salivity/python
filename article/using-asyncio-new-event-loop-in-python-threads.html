Using asyncio.new_event_loop in Python Threads

This article explains the purpose and implementation of asyncio.new_event_loop() when working with secondary threads in Python. Python's asyncio framework assigns a default event loop to the main thread, but background threads lack one by default. Understanding how asyncio.new_event_loop() creates, configures, and isolates an independent asynchronous runtime is essential for safely running concurrent coroutines inside secondary threads without interfering with the main thread or causing runtime errors.

The Role of asyncio.new_event_loop()

In Python, the asyncio event loop is not thread-safe. A single event loop instance cannot safely execute tasks across multiple threads simultaneously. To run asynchronous code inside a secondary OS thread (such as one created using threading.Thread), that thread must have its own isolated event loop.

By default, calling asyncio.get_event_loop() inside a secondary thread raises a RuntimeError: There is no current event loop in thread in modern Python versions. The asyncio.new_event_loop() function solves this by explicitly constructing a new, unattached AbstractEventLoop instance configured specifically for that thread's execution context.

Managing the Lifecycle on a Secondary Thread

Creating the loop object is only the first step. To execute coroutines reliably within a worker thread, you must manage the loop's full lifecycle: creation, association, execution, and cleanup.

  1. Creation: Calling loop = asyncio.new_event_loop() allocates a fresh event loop instance.
  2. Association: Calling asyncio.set_event_loop(loop) registers the newly created loop as the current active event loop for the calling thread. This ensures that any nested functions or third-party libraries calling asyncio.get_running_loop() or asyncio.get_event_loop() resolve to this specific loop.
  3. Execution: The thread starts the loop using either loop.run_until_complete(coroutine()) for bounded tasks or loop.run_forever() for persistent background listeners.
  4. Cleanup: Once execution finishes, the loop must be shut down gracefully using loop.close() to release underlying OS selectors, sockets, and resources.

Standard Implementation Pattern

The following pattern illustrates how asyncio.new_event_loop() is typically implemented inside a worker thread function:

import asyncio
import threading

def worker_thread():
    # 1. Create a new independent loop for this thread
    loop = asyncio.new_event_loop()
    
    # 2. Assign the loop to the current thread's context
    asyncio.set_event_loop(loop)
    
    async def sample_coroutine():
        await asyncio.sleep(1)
        return "Task finished"

    try:
        # 3. Run the task within this thread's loop
        result = loop.run_until_complete(sample_coroutine())
        print(result)
    finally:
        # 4. Clean up pending tasks and close the loop
        loop.run_until_complete(loop.shutdown_asyncgens())
        loop.close()

# Start the secondary thread
thread = threading.Thread(target=worker_thread)
thread.start()
thread.join()

Comparison with asyncio.run()

In Python 3.7 and later, asyncio.run() serves as a higher-level convenience function. When called within a secondary thread, asyncio.run() internally calls asyncio.new_event_loop(), sets it as the active loop, runs the target coroutine, and closes the loop automatically upon completion.

However, direct usage of asyncio.new_event_loop() remains necessary when:

  • The worker thread requires a persistent, long-running loop that must stay open across multiple separate calls using loop.run_forever().
  • Thread-safe scheduling from other threads is required via asyncio.run_coroutine_threadsafe(coro, loop).
  • Custom event loop policies or specific lifecycle hooks need to be configured before execution begins.
