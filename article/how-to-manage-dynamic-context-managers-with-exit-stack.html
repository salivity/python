How to Manage Dynamic Context Managers with ExitStack

In Python, standard with statements require you to define every context manager statically at write-time, which becomes impossible when the number of resources depends on runtime data. The contextlib.ExitStack class solves this problem by providing a programmatic, stack-based API to enter, track, and cleanly exit an arbitrary number of context managers. This article explores how ExitStack works, how to use it to manage dynamic resources, and how it handles exceptions and resource cleanup in Last-In, First-Out (LIFO) order.

The Limitation of Standard with Statements

A conventional with statement can manage multiple context managers if they are hardcoded:

with open("file1.txt") as f1, open("file2.txt") as f2:
    # Work with f1 and f2
    pass

However, if you receive a dynamic list of file paths at runtime—such as a list of 10, 50, or an unknown number of files—nesting with statements manually or chaining them statically is not feasible. Attempting to manage them in a naive loop using a try...finally block often leads to resource leaks if an error occurs midway through initialization.

How ExitStack Works

contextlib.ExitStack acts as a container that manages a dynamic stack of exit callbacks. When you instantiate ExitStack as a context manager, it provides methods to register other context managers programmatically.

As resources are registered, ExitStack stores their __exit__ methods internally. When the ExitStack block terminates—either normally or due to an unhandled exception—it invokes these exit methods in reverse order (LIFO), replicating the exact unwinding behavior of nested with blocks.

Registering Resources Dynamically with enter_context

The primary method for dynamic management is enter_context(cm). It takes an active context manager, calls its __enter__ method, adds its __exit__ method to the internal stack, and returns the result of the __enter__ call.

Here is an example of opening a variable list of files safely:

from contextlib import ExitStack


def process_files(file_paths):
    with ExitStack() as stack:
        # Dynamically open and track every file
        files = [stack.enter_context(open(path, "r")) for path in file_paths]

        # All files are guaranteed open here
        for f in files:
            data = f.read()
            # Process data
            print(f"Read {len(data)} characters from {f.name}")

    # All files are guaranteed closed here

If opening the fifth file raises an OSError (e.g., file not found), ExitStack catches the failure, calls __exit__ on the four previously opened files in reverse order, and then propagates the exception. No open file handles are leaked.

Adding Arbitrary Cleanup Callbacks

ExitStack is not limited to standard context managers that implement __enter__ and __exit__. You can register arbitrary cleanup logic using:

  • stack.callback(func, *args, **kwargs): Registers any callable to be executed on exit.
  • stack.push(exit_callback): Accepts custom __exit__-compatible functions or objects implementing context management protocols.
with ExitStack() as stack:
    stack.callback(print, "Cleanup step completed.")
    # Business logic here

Transferring Ownership with pop_all

There are scenarios where resources must outlive the scope that created them—for example, inside a factory function or an object initialization method. If setup fails halfway through, you want to clean up existing resources, but if setup succeeds, you want to preserve them.

The pop_all() method transfers all active callbacks to a new ExitStack instance, preventing the current stack from closing them upon scope exit:

from contextlib import ExitStack


def open_transaction_bundle(paths):
    with ExitStack() as stack:
        resources = [stack.enter_context(open(p, "w")) for p in paths]

        # Transfer ownership to prevent cleanup on return
        new_stack = stack.pop_all()
        return resources, new_stack

If an error occurs before stack.pop_all() is executed, all currently opened files are immediately closed. If execution reaches stack.pop_all(), the caller receives the open resources and the new stack responsible for closing them later.
