Using types.coroutine to Bridge Python Generators

Python's types.coroutine decorator serves as a vital compatibility bridge between legacy generator-based coroutines and modern native coroutines defined with async def. Introduced in Python 3.5, it converts a standard generator function into an object that can be recognized as a coroutine, allowing developers to await generator-based code directly within native coroutines without rewriting the underlying yielding logic.

The Historical Divide

Before Python 3.5, asynchronous programming relied heavily on standard generators. Libraries like asyncio used the @asyncio.coroutine decorator combined with the yield from syntax to pass futures and control back to an event loop.

When Python 3.5 introduced native coroutines via async def and await, it established a strict separation: native coroutines could not directly await standard generators to prevent accidental misuse of regular iterators. However, this created a backward-compatibility problem for existing codebases and low-level libraries that needed to yield raw futures to event loops.

How types.coroutine Works

Under the hood, types.coroutine sets an internal flag (CO_ITERABLE_COROUTINE) on the code object of the decorated generator function.

This flag signals to Python's runtime that the generator is intended to be used as a coroutine. As a result:

  1. Awaitability: The wrapped generator satisfies the collections.abc.Coroutine interface rules and can be used in an await expression inside an async def function.
  2. Yield Preservation: Unlike native async def functions—which cannot use plain yield expressions to suspend execution without becoming asynchronous generators—a types.coroutine can still yield values (such as asyncio.Future instances) directly down the call stack to an event loop driver.

Practical Implementation

The following example demonstrates how a generator-based coroutine can be called seamlessly from a native async def coroutine:

import types
import asyncio

@types.coroutine
def legacy_sleep_step():
    # Yield control directly, behaving like low-level asyncio internals
    yield

async def main():
    print("Starting native coroutine...")
    # Directly awaiting the generator-based coroutine
    await legacy_sleep_step()
    print("Resumed and finished.")

asyncio.run(main())

Without the @types.coroutine decorator, attempting to await legacy_sleep_step() raises a TypeError: object generator can't be used in 'await' expression.

Primary Use Cases

  • Low-Level Event Loop Interaction: Modern native coroutines cannot yield arbitrary objects directly to an event loop scheduler; they can only return or await other awaitables. types.coroutine provides a loophole for framework authors to implement primitive suspension points.
  • Incremental Migration: It allows large codebases using deprecated @asyncio.coroutine syntax to interface with modern async/await functions without requiring an immediate, complete rewrite of all generator-based asynchronous functions.
  • Cross-Compatibility: Library authors can build libraries that integrate with both older generator-based frameworks and modern asynchronous ecosystems.
